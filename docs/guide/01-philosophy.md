## 一条原则

上游把整个项目归结为一句话：

> **Take as little human attention as possible, and give as much value as possible.**
> 占用尽量少的人类注意力，产出尽量多的价值。

这句话读起来像口号，但上游把它当作可执行的判据："每条消息、通知、问题、设置、面板元素、文档段落都要花掉某人的注意力，它给出的价值必须超过这个成本，否则就删掉。"

为什么要把这条原则放在第一位？一个能代表整个团队行动的 agent，同样能浪费整个团队的注意力。单人用的 coding agent 话多一点，只影响用它的那个人。这个 agent 用一个团队每天都能看到的 GitHub 账号发言，每条多余的评论都会推送给所有关注这个仓库的人。

## 推出来的行为约束

上游列了五条。下表把每条和它在代码或 prompt 里的落点对应起来，后续章节会展开。

| 约束 | 含义 | 落点 |
| --- | --- | --- |
| 只在被请求、或成文规则允许时行动 | 请求必须直接对着 agent，并且来自团队允许的人。没人请求的工作需要团队写一条规则，而且起步只记录不执行 | Gate 与接单模式 `observe`，见 [04 授权](./04-authorization) |
| 只在有人必须行动、或能用上结果时说话 | 确认一次，干活时安静，有结果、要决定、做不完时再说 | `Replies` 只允许四种用途的消息：确认、回答、结果、待决问题。见 [03](./03-request-lifecycle#step-6-ack) |
| 一次问一个具体问题 | 用结构化字段问，问题才不会埋在长报告里 | `orchestrator_report` 的 `human_action` 字段，见 [07 Prompt](./07-prompts) |
| 按影响而不是按工作量决定停在哪 | 局部改动做到可评审为止；需要设计决定的改动带着问题停下 | 团队 prompt 段落 Ticket scope |
| 如实报告 | 草稿标为未完成，失败就报失败，不绕过限制来避免提问 | 团队 prompt 段落 Delivery requirements |

## 推出来的设计约束

这条原则对**设计者**同样适用，因为概念、设置、面板元素和文档也都花读者的注意力：

- **概念少。** 业务需求要么变成已有概念的一个属性，要么变成 agent 读的一段 prompt，不新增概念。上游 001 有一张"被拒绝的概念"表，专门记录为了守住这一条拒绝了什么。见 [02 领域模型](./02-domain-model)。
- **设置少。** 一个值几乎适合所有团队时，用默认值代替设置项。团队能用文字描述的行为写成 prompt，不做成开关。
- **面板只显示需要人的东西。** 健康状态不占空间。见 [08 面板](./08-panel)。
- **文档按顺序读。** 每篇编号文档只依赖前面的文档，读者不会碰到还没介绍的概念。

"团队能用文字描述的行为写成 prompt"这一条值得多看一眼。很多系统会给"PR 合并前需要谁批准"做一个配置项。dsh-superagent 把它写进 Delivery requirements 这段 prompt，由执行器去遵守。合并规则真正的强制要靠 GitHub 的分支保护，上游 <Doc page="003-execution" anchor="merging">003 · 合并</Doc> 明确这么说。代价是"遵守"变成了模型行为而非代码保证；好处是团队可以用自然语言表达任意复杂的流程，系统不用为每种流程长出一个开关。

## 运维者的责任

部署这个 agent 的人（上游叫 operator）要为它说的每句话负责。上游给了四条：

1. **从窄处开始。** 短的允许名单，主动工作只记录。看过记录、觉得它的判断靠谱，再放宽。
2. **为减少噪音而调整。** agent 太吵时，让 prompt 更短更严，或者暂停它。不要再加消息去解释噪音。
3. **不要用它制造数量。** 批量 PR、广播消息、凑数的工作，给团队带来的成本大于价值。
4. **为它说的话负责。** 读它以你的名义发的东西，错了就去改 prompt。

SETUP.md 本身就是这条原则的一个示范：安装由你的 coding agent 带着做，一次只问一个问题，每条消息不超过 300 词，问完所有问题再一次性给出计划。见 <Doc page="setup" anchor="how-to-run-the-setup">SETUP · 如何进行安装</Doc>。

## 和常见 agent 的对比

| | 常见的对话式 coding agent | dsh-superagent |
| --- | --- | --- |
| 服务对象 | 一个人 | 一个仓库和它的团队 |
| 何时行动 | 用户发消息时 | 被允许的人 @ 它时，或成文规则允许时 |
| 谁能指挥 | 用户 | 允许名单上的人；其他人的消息只是上下文 |
| 汇报方式 | 实时流式输出 | 在原对话里确认一次、交付一次 |
| 中途提问 | 随时问 | 一次一个结构化问题，转发到提问人所在的位置 |
| 失败 | 用户看着它失败 | 报告 `blocked` 或 `failed`，面板显示等待人处理 |

## 思考题

1. 上游说"Do not add more messages to explain the noise"。设想 agent 在某个 Issue 里误解了需求，发了一条错误的确认。按这条原则，正确的处理方式是什么？
2. "设置少"和"每个团队需求不同"之间有张力。dsh-superagent 用 prompt 段落来承接差异，这种做法在什么情况下会出问题？
