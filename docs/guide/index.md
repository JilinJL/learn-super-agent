# 导读：SuperAgent 是什么，为什么值得学

让 agent 写出第一版代码之后，开发任务往往还要继续。

测试可能失败，评审可能要求修改；你暂时没空回答它的问题，服务也可能中途重启。如果同时有几件事在做，还要有人记住：谁在处理哪件事，哪些可以继续，哪些需要等人决定。

这些衔接工作，平时很容易落到使用 agent 的人身上。SuperAgent 值得研究的地方，就是它尝试用一套系统来承担这些工作。

[**dsh-superagent**](https://github.com/deepseek-ai/dsh-superagent-prototype)（下文简称 SuperAgent）是 DeepSeek 开源的编码 agent 研究原型：**它通过主 Agent 调度、独立执行器和持久化的任务记录，组织需要多轮推进的开发工作，并把关键决定交还给人。**

这套教程围绕三个问题展开：**长任务怎样持续推进，多个 Agent 怎样分工，人怎样监督而不必一直盯着。**

![主 Agent 协调三个独立执行器；各自的任务记录保存已完成与待完成的工作，只有需要决定的问题才交给人](/images/guide-continuous-work.png)

*图中的工作台代表不同任务。每个执行器保留自己的工作记录，调度员负责协调，人参与需要判断的环节。*

## 先看一个还没做完的任务 {#a-first-look}

假设你请 agent 修复结算页的金额显示问题。它找到原因、改好代码，开了一个 PR。

然后呢？

| 接下来发生的事 | 系统需要接住什么 |
| :--- | :--- |
| 测试失败了 | 把反馈交给正在处理这件事的执行器，继续排查 |
| 评审提出修改意见 | 让意见回到原来的任务，保留已经做过的工作 |
| 有两种修改方案，需要你选择 | 说清楚要决定什么，等待回答 |
| 等你回答时，另一个任务来了 | 继续调度其他工作，避免所有事情一起停住 |
| 执行服务重启了 | 找回任务、工作目录和待处理消息，按恢复规则继续 |

这里的一件事，已经跨过了多次模型调用、多轮对话，以及一段等待时间。

**任务怎样保持连续，是我们要学的第一个问题。** 接下来再看：当这样的任务同时有好几个时，系统怎样安排它们；需要人介入时，又怎样把事情交代清楚。

## 它主要在回答三个问题 {#the-problem}

### 1. 长任务怎样持续推进？ {#recovery}

这里的“长”，可以先理解为：一件工作需要多轮执行和反馈才能完成，中间还可能暂停、失败或重启。

SuperAgent 用 **Ticket** 记录这件工作，用 **Assignment** 记录它与一次执行的绑定。一个 Ticket 在不同时间可以有多个 Assignment，任务自己的状态与执行器的状态分别记录。

这样，一次执行结束后，系统仍能知道这件事是否完成、在等什么、还有哪些输入没有处理。重试和恢复也可以沿用原来的 Session、目录和工作成果，再检查下一步该做什么。

读到 [**05 执行**](./05-execution) 和 [**06 可靠性**](./06-reliability) 时，我们会具体看这些记录怎样支持继续工作，以及哪些中断需要额外处理。

### 2. 多个 Agent 怎样分工和协调？ {#roles}

SuperAgent 把调度和技术执行分给不同角色：

- **主 Session（orchestrator）：** 评估新请求、接单和路由，协调需要转交的信息。
- **执行器 Session（worker）：** 负责一个 Ticket 的调查、实现和验证，有自己的工作目录，也可以使用 DSH 提供的子 Agent。

如果执行器正在跑一个耗时测试，主 Session 仍应能处理其他请求。后台工作完成后，再通过事件唤醒相关执行器。并发槽位则控制同一时间有多少工作在执行。

这里值得观察的“监管”，是明确的职责、执行状态、授权和交接规则。主 Session 主要做路由，具体技术判断和验证由执行器负责。

我们会在 [**05 · 并发与槽位**](./05-execution#slots) 和 [**07 Prompt**](./07-prompts) 中，看看这套分工怎样同时落实到提示词和代码里。

### 3. 人怎样监督，而不必一直盯着？ {#attention}

你需要知道的是：有没有事情卡住，什么结果可以评审，现在是否需要自己作决定。

为此，执行器会报告工作状态；需要人回答的问题通过结构化字段提出，再送到合适的对话中。面板把待回答、待评审、受阻或失败的工作呈现出来，让人能找到下一步该处理的事。

上游把这个目标概括为：**尽量少占用人的注意力，尽量多创造价值。** <Doc page="000-philosophy">000 设计哲学</Doc>

这也解释了它为什么强调少发进度消息、一次问一个具体问题、如实标记未完成的结果。我们会在 [**01 设计哲学**](./01-philosophy) 和 [**08 面板**](./08-panel) 中展开。

## 从这些问题进入代码 {#the-answer}

第一次读时，不必记住全部术语。先把几个名字和它们要解决的问题对应起来：

| 你关心的问题 | 代码中的主要机制 | 在哪里展开 |
| :--- | :--- | :--- |
| 一件事怎样跨过多轮执行？ | Ticket、Assignment、持久化状态与恢复 | [05 执行](./05-execution)、[06 可靠性](./06-reliability) |
| 谁负责调度，谁负责实现？ | 主 Session、执行器 Session、并发槽位 | [07 Prompt](./07-prompts)、[09 代码架构](./09-architecture) |
| 新消息怎样回到正在做的任务？ | Thread、Subscription、跟进投递 | [02 领域模型](./02-domain-model)、[03 一个请求的一生](./03-request-lifecycle) |
| 谁能让 agent 开始工作，允许做到哪里？ | Gate、Policy、Mandate | [04 授权](./04-authorization) |
| 人怎样发现自己需要介入？ | 结构化报告、待决问题、面板 | [05 执行](./05-execution)、[08 面板](./08-panel) |

这些机制需要配合起来。持久化保存状态，执行器继续工作，订阅把后续反馈送回来，授权规定工作范围，面板帮助人决定何时介入。

读到一段实现时，可以试着问：**如果去掉它，刚才那件还没做完的任务会在哪一步接不上？**

## 用开发流程串起这些机制 {#github-as-example}

本教程会沿着一次 GitHub 仓库中的开发任务展开：从收到请求，到执行器修改代码、提交 PR，再到接收 CI 和评审反馈、继续修改、交付结果。

每一步都能对应到前面的问题：新请求由谁处理，反馈怎样回到原来的任务，等待评审时怎样安排其他工作，重启后又从哪里继续。带着这些具体情况读代码，任务、调度和恢复之间的联系会更清楚。

阅读时，可以同时留意两层设计：

- **平台接入：** GitHub 和可选的飞书怎样把外部事件转成系统能处理的输入，又怎样把结果送回讨论。
- **任务管理：** 系统怎样记录工作、安排执行器、传递后续反馈，并在需要时交给人决定。

到 [**10 扩展**](./10-extending)，我们会沿用这套领域模型接入新的来源，看看 Source、Executor 和 Channel 的具体实现怎样与核心规则配合。

## 为什么值得花时间读它 {#why-learn}

如果你已经做过一个“收到消息就调用模型”的应用，这个项目适合帮助你继续思考：

1. **一次调用怎样变成持续的任务。** 你会看到任务状态、执行记录和外部反馈怎样衔接，理解失败、等待和恢复为什么需要各自的规则。
2. **多 Agent 的分工怎样变成可执行的约束。** 除了写明角色，还要限制工具、安排并发、定义报告，并处理后续消息的归属。
3. **怎样给人保留足够的控制。** 授权范围、待决问题和评审交接，会影响人能否放心地把工作交出去。

它也适合练习对照文档读代码。上游文档描述规则，代码注释引用对应编号，教程再补充场景和解释。遇到一个设计决定，可以一路追到它的依据和实现。

例如，为什么任务状态不直接跟着执行器 Session 走？为什么不让主 Session 等待长命令？这些取舍收在 [**被拒绝的设计**](/appendix/rejected-designs) 中，可以和正文一起读。

## 开始之前，了解它的适用范围 {#scope}

**本文讨论的是公开的研究原型。** 上游说明它尚未达到生产就绪状态，与内部版本、文章 *Exploring Super-agent Design* 中描述的实现也不完全相同。文章中的部分设计方向没有在这个原型中实现。

**理解它的长任务能力，要看具体的继续与恢复规则。** 任务能够保留记录、接收后续反馈，并不意味着模型可以无限保持上下文，也不意味着每一种外部操作都能自动、安全地重做。

**理解它的多 Agent 能力，要看具体的角色职责。** 主 Session 主要负责评估和路由；技术调查、实现、验证由执行器承担。自主发起的工作也需要团队预先提供规则，并从只记录“本来会做什么”的模式开始。

它以 **DeepSeek Harness（DSH）的 bundle** 形式运行，Session、工具调用和面板等能力由 DSH 提供。你不需要提前熟悉 DSH；教程会在涉及这些能力时说明它的作用。

## 从哪里开始读 {#reading-paths}

- **想先建立整体印象：** 读 [**03 一个请求的一生**](./03-request-lifecycle)，跟着一条请求走过接单、执行和反馈。
- **关心长任务和恢复：** 接着读 [**05 执行**](./05-execution) 与 [**06 可靠性**](./06-reliability)，重点看任务何时等待、怎样继续，以及重启后保留什么。
- **关心多 Agent 分工和人的监督：** 读 [**07 Prompt**](./07-prompts) 与 [**08 面板**](./08-panel)，观察角色、工具和交接怎样配合。
- **准备读源码或动手实现：** 从 [**09 代码架构**](./09-architecture) 找到入口，再跟着 [**11 最小复刻**](./11-build-your-own) 跑通核心模型。最小示例的 worker 使用 stub，真实编码执行器属于后续扩展。

读完整套教程后，你应该能解释：**一件工作为什么能跨过多轮执行，多个执行器为什么能各自推进，以及系统在什么情况下应该把下一步交给人。**
