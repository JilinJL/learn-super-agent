# 000 设计哲学 {#_000-philosophy}

<UpstreamBanner kind="translation" />

dsh-superagent 是一个框架，也是一种与 agent 协作的方式。它的核心原则是：

**尽可能少占用人的注意力，尽可能多地提供价值。**

项目的每个部分都按它消耗的注意力来评判。一条消息、一个通知、一个问题、一项设置、一个面板元素和一段文档，都会消耗某个人的注意力，每一项都必须带来比这更多的价值，否则就被删掉。

## 对 agent 的要求 {#what-follows-for-the-agent}

- **它只在被请求时、或书面规则允许时才行动。** 一个请求只有在直接对 agent 说、并且来自团队允许的人时才算数：要么是允许名单上的人，要么是团队开放了请求的对话中的任何人。没人请求的工作需要团队写下的规则，并且一开始处于只记录 agent 本来会做什么的模式。
- **它只在有人必须采取行动或能用上某个结果时才发言。** 它对一个请求只确认一次，并说明它要做什么。工作期间它保持安静。当结果就绪、需要一个决定、或无法完成时，它才再次发言。消息要简短，并发到提出请求的那个对话里。
- **它一次只问一个具体的问题，** 并采用结构化的形式，让问题真正送到人面前，而不是埋在一份长报告里。
- **它按影响决定在哪里停下，而不是按工作量。** 局部改动一直做到可供审阅的结果为止。需要设计决定的改动则停下来，提出一个清楚的问题。
- **它如实报告。** 草稿标明未完成，失败就报告为失败，绝不为了避免提问而绕过限制。

## 对设计的要求 {#what-follows-for-the-design}

- **概念少。** 设计中只有它的领域概念，例如 Source（来源），以及这些概念的具体实现，例如 GitHub 和飞书。一项业务需求要么成为其中某个概念的属性，要么成为 agent 遵循的一段 prompt。设计不会为它新增概念。
- **设置少。** 当某个取值几乎适合每个团队时，就用默认值代替设置。团队用文字描述的行为是 prompt 文本，而不是设置。
- **面板只展示需要人处理的事项。** 它首先列出等待人处理的事项。健康状态不占空间。
- **文档按顺序阅读。** 每篇编号文档只建立在前面几篇之上，因此读者永远不会遇到一个尚未介绍的概念。

## 责任 {#responsibility}

agent 会以你的团队每天都能看到的账号发表评论、开 pull request、给人发消息。它发出的每条消息都会消耗你同事的注意力，而你要为此负责。agent 能做的越多，它的运维者就越要对团队用心：

- **从窄处开始。** 先用一份短的允许名单，主动工作只做记录。等 agent 本来会做的事看起来都对了，再把两者放宽。
- **调优以减少打扰。** 当 agent 太吵时，把它的 prompt 改得更短、更严格，或者暂停它。不要再加更多消息去解释这些打扰。
- **不要用它来制造数量。** 批量的 pull request、群发消息和无意义的忙碌，给团队带来的成本超过它们的价值。
- **为它说的话负责。** 阅读 agent 以你的名义发布的内容，它出错时在 prompt 中纠正它。

目标是在合适的时候给出合适的帮助，其他任何时候都不打扰。
